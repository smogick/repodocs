Правила в [CLAUDE.md](../../CLAUDE.md) говорят *как писать*. Этот чек-лист — *что именно проверить*, чтобы в базе не накапливался мусор. Применяй его в двух режимах:

- **На лету** — при любом значимом изменении карточки (см. "Обязательно при правке" ниже).
- **Периодически** — раз в несколько недель или когда пользователь просит "проверь доки", пройдись по всем карточкам из [INDEX.md](../../INDEX.md).

## Обязательно при правке карточки

Эти пункты — не отдельный ревью-проход, а часть самой правки. Не заканчивай правку, не пройдя их:

1. **`updated` обнови на сегодняшнюю дату**, если менял что-то содержательное (не опечатку).
2. **Если у карточки есть `journal.md`** и изменение достаточно значимое — добавь туда запись с датой. Если `updated` в README свежее последней записи журнала больше чем на пару недель — это сигнал, что либо журнал забросили, либо `updated` дёрнули не по делу. Синхронизируй.
3. **Новый файл в карточке — проверь, что на него можно попасть.** Либо он упомянут/сссылается из README, либо явно помечен как черновик (см. пункт про статус ниже). Файл, до которого можно дойти только через файловый список — то же самое, что файл, которого нет, и для человека, и для агента.
4. **Новый черновик/предложение без явного статуса** (не готовая фича, а идея/proposal) — добавь в начало файла одну строку: `Статус: черновик` / `Статус: заменено на X` / `Статус: отклонено`. Без этого через месяц никто не поймёт, живая это идея или нет.
5. **`type` соответствует содержимому.** Если файл на самом деле справочный (доступы, инструкция использования, конфигурация) — `type: resource`, а не `project`, даже если он лежит в `projects/`.

## Периодический проход (по каждой карточке из INDEX.md)

- [ ] **Frontmatter не врёт**: `status`/`stack`/`tags`/`summary` соответствуют актуальному телу файла, а не тому, что было на момент создания карточки.
- [ ] **Ссылки резолвятся.** Особенно после переименований/переносов — относительные ссылки (`../../resources/glossary.md` и т.п.) молча ломаются при перемещении файла.
- [ ] **Название файла отражает содержимое.** Плохой пример: `notes.md`, `resources.md` с узким конкретным содержимым внутри — расплывчатое имя прячет суть, лучше `lists-ux-notes.md`, `project-resources-acl-draft.md`.
- [ ] **Нет дублирования между карточками без явной связи.** Два глоссария/два файла с одинаковой темой в разных карточках — нормально, если у каждого чётко описан свой scope и они ссылаются друг на друга; плохо, если это просто копипаста или неявное пересечение.
- [ ] **Пустые заглушки-плейсхолдеры** (`status: idea`, тело — одна строка "пока не наполнено") — либо удали, либо оставь только если реально есть план наполнить в обозримом времени.
- [ ] **README не превратился в свалку.** Если файлов в карточке много (10+), README должен группировать/объяснять, какой файл за что отвечает — не просто список.
- [ ] **Секреты не просочились.** Быстрый grep на `password|token|secret|api_key|BEGIN.*PRIVATE` по изменённым файлам (см. правило в [frontmatter.md](frontmatter.md#правило-про-секреты)).

## Автоматическое обнаружение "протухания"

В UI карточки, где реальные файлы менялись позже, чем указано в `updated` frontmatter, помечаются иконкой ⚠ — это значит, что содержимое поменяли, а `updated` забыли обновить (пункт 1 выше). Не игнорируй эту метку молча — либо обнови `updated`, либо (если правка была тривиальной и правда не стоит внимания) осознанно оставь как есть.

Пересборка INDEX.md (`npm run build-index` в repodocs) также запускается автоматически при каждом сохранении README из UI — вручную его гонять нужно только если правишь файлы вне UI (напрямую в файловой системе).
